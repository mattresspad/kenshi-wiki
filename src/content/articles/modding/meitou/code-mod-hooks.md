A MeitouClient code mod is a C# library loaded beside a data mod. Supported hooks provide defined extension points; each has its own threading, ownership, persistence and failure rules. Harmony patches can reach beyond those contracts, but do not inherit their guarantees.

This is **bounded coverage of teppuM’s PR #44 draft**, not every hook or a guarantee for newer clients. The tables distinguish **MeitouClient 0.22.1**, **nightly v0.22.2-nightly.20261119.2**, and **later source 86d0af2**. Later source changes are not evidence of inclusion in a release. Launcher versions do not establish client API availability. Verification here is source inspection, not an in-game test.

Start with [Meitou community mods](/modding/meitou#make-a-code-mod) and the maintained [code-mod guide][guide]. The [version-evidence matrix](/notices/code-mod-hooks-evidence.json) preserves each draft claim, pinned implementation/documentation links, qualifications and review results. The [pinned later reference][reference] describes a newer contract where noted.

A matching Meitou.References package can support compilation without a local game install. The pinned publication workflow attempts packages for full client releases, may continue if publication fails, and does **not** publish packages for nightlies. Confirm that the matching package exists before following that build route. Publicized internal APIs may change between releases. [Reference-package rules][refpack]

## Rules to know first

- The `Add...` calls on your mod's context work only inside your mod's `Initialize`. Interface rows are added later, from your interface extension.
- Don't change game records in `Initialize`: by then much is already built from them. Change them in the data phase (below).
- Registered dialogue codes, record types, job types and applicable goal types a mod claims start at 1000, and a number another mod already claimed refuses the second mod. One mod may use the same number as both its job type and its goal type. Weather kinds use numbers from 1000 up too, but nothing checks for clashes.
- Names that every mod shares, such as carry modifier keys, status effect ids and weapon class names, should start with your mod's id (`mymod.whip`), so two mods never pick the same one.
- A character's id changes at every load. Keep data about a character under its lasting id (below), never under its ordinary id.
- The simulation must repeat exactly. Roll random numbers with `Rng.Hash` and your mod's `RngPurpose`, never `Random`. In the parallel parts of a tick, change only the character you're stepping. Change the rest of the world only in serial steps, and never from outside the tick.
- Callback contracts differ. Most observers queue gameplay changes; pure filters must not mutate their own answer-producing state. Experience filters can run concurrently. Relation observers explicitly permit relation changes through the documented API, while forbidding unrelated world mutation.
- Interface code runs while a tick may be in progress, so it never touches the world. It reads what it's given and queues commands.
- Failure behavior is specific to the hook and version: some callbacks are disabled, some return a fallback and remain callable, and a system can be stopped. IGoalSource.Publish exceptions are not caught as mod faults. A failed data phase can leave earlier changes merged. Do not assume atomic rollback or universal recovery.

## Running your own logic

Your changes merge in mod-list order, after every data file. A mod that throws here is left out, and changes it already merged stay for the session. | **post-0.22.1; present in pinned nightly.** Data-phase edits are not transactional: changes already merged remain if a mod later fails. | [`AddSystem`][systems] | Run a system at a selected tick anchor. A source interface looked up by first match can replace the corresponding standard source when placed earlier; inserting before an arbitrary system does not replace that system. | **API present in 0.22.1.** Only source interfaces resolved by first match can replace a standard source. Placement before an arbitrary system is not a general replacement API; missing anchors append at the end. [Source](https://github.com/VlcekM/MeitouClient/blob/9ee4074bbc6fd7fdeb26108a04afc9f90cb1dc01/src/Meitou.Simulation/World.cs#L633) |

Use it to set up again whatever isn't saved. | **API present in 0.22.1.** Runs between ticks, after save loading and before the first tick. [Source](https://github.com/VlcekM/MeitouClient/blob/9ee4074bbc6fd7fdeb26108a04afc9f90cb1dc01/src/Meitou.Game/Mods/ModContext.cs#L371) |

[Source](https://github.com/VlcekM/MeitouClient/blob/9ee4074bbc6fd7fdeb26108a04afc9f90cb1dc01/src/Meitou.Game/Mods/ModContext.cs#L357) |

| Hook | What it lets a mod do | Version and limits |
|---|---|---|
| `SetSquadAutonomy` | Let the AI run one of the player's squads on AI packages (`ChangeAi`, `StartContract`), with a home (`SetSquadHome`). An independent squad stays in the player's faction, but the player doesn't lead it: for staff, caravans or companions. A home in one of the player's outposts makes that outpost the squad's town. Its right-click menu has no inventory row, but your mod can add one that opens the member's inventory (`OpenLootOrder`), for handing out uniforms. | **API present in 0.22.1.** Ownership cleanup restores specified squad settings; it does not undo all effects a mod caused. | [`SetSquadShop`][shops] | Turn an independent squad of the player's faction, with its own purse, into shopkeepers the player trades with in the ordinary trade window. The shop uses the squad's own money, never the player's, and its stock comes from a trader's squad template or from your mod. ## Working with other mods

| Hook | What it lets a mod do | Version and limits |
|---|---|---|
| [Dependencies][dependencies] | List in `meitou.json` the mods yours needs, loads after or can't run with, and the game versions it was built for. Nothing reorders the mod list: if the order is wrong, your mod is refused with a message saying what to move. A mod can use another mod's code directly (`Dependency<T>`), so a shared framework loads only once. `IModDependents` tells a framework when a mod built on it fails to start. | **API present in 0.22.1.** Dependencies validate order; they do not reorder mods. Direct shared code requires the declared dependency and compatible APIs. [Source](https://github.com/VlcekM/MeitouClient/blob/9ee4074bbc6fd7fdeb26108a04afc9f90cb1dc01/src/Meitou.Core/Content/ModList.cs#L233) |
| [Harmony][harmony] | Patch the game's code for anything no hook covers. The client loads one copy of Harmony and gives it to every mod. | **API present in 0.22.1.** Harmony shares the client-loaded library but provides no compatibility, determinism or rollback guarantee for arbitrary patches. [Source](https://github.com/VlcekM/MeitouClient/blob/9ee4074bbc6fd7fdeb26108a04afc9f90cb1dc01/src/Meitou.Game/Mods/ModContext.cs#L101) |

A data mod that reshapes the whole game, such as a conversion, should edit the [records the engine looks up by id or name][fixedids] in place rather than removing or renaming them. That list says what each one is for, and what happens without it.

Data mods can also swap game files and add sound banks through `RE_Kenshi.json` without any code. MeitouClient reads its `SoundBanks` and its `FileRebinds`, which swap the map files, the map's color tiles and files found through the game's resource groups. In the pinned nightly, a rebind also reaches meshes, skeletons, textures, icons, interface layouts and collision files, and can hide a file. MeitouClient never runs RE_Kenshi plugins. Instead, a plugin gets ported as a code mod of its own on the Steam Workshop, and the launcher offers to subscribe to the ports Meitou endorses. To bring an RE_Kenshi mod over, see [Does my RE_Kenshi mod need a port?](/modding/meitou/porting-re-kenshi-mods)
